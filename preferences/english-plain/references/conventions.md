# Writing conventions

Use these only where the project has no convention of its own. They apply to prose. Code, data tables, and direct quotations keep their own conventions.

## Spelling and capitalization

- Use one spelling variant (US or UK) across the product. Follow the project's existing choice.
- Use sentence case for headings, subheadings, buttons, labels, and table headers. Capitalize only the first word and proper nouns.
- Capitalize a product or feature name only when it is the official name.
- Do not use all caps for emphasis. It reads as shouting, and some screen readers spell it out letter by letter.
- In a hashtag, capitalize each word (#PlainLanguage) so screen readers can read it.

## Punctuation

- End complete sentences with a period, including list items that are full sentences.
- Do not join two sentences with a comma.
- Use the serial comma when it prevents ambiguity.
- Use an exclamation mark only in a warm success message, and never more than one.
- Use an em dash rarely, and at most once in a paragraph.
- Use quotation marks for direct quotes and document titles. Do not use italics for titles.
- Avoid semicolons in user-facing text. Two short sentences are clearer.

## Numbers

- Use numerals for 10 and above, for any number with a unit, and for counts in an interface ("3 items"). Spell out one to nine in running prose.
- Put the % symbol directly after the number: 50%.
- Put the currency symbol and separators where the reader's locale puts them: $75 in the US, Rp75.000 in Indonesia. Never mix styles in one document.
- Write large numbers in words when it helps: "$5 million", not "$5M" or "$5,000,000".
- Use "to" in ranges: "10 to 20 people". Screen readers may read a hyphen or dash as "minus".

## Dates and times

- Write "4 June 2026", without ordinals such as "4th". Never write 04/06/26. If the project or audience uses "June 4, 2026", follow that.
- For a date range, write "Monday 1 June to Friday 5 June 2026". Check each weekday against a calendar before you write it.
- Write time as "10 a.m." or "10:30 a.m.", or use the 24-hour clock ("14:00") throughout if the audience expects it.
- For a time range, write "10 a.m. to 11:30 a.m."
- State the time zone when readers may be in several: "10 a.m. WIB".

## Formatting

- Do not use bold or italics for emphasis. Use bold only for the literal name of an interface element in an instruction: select **Save**.
- Markdown headings and lists are fine, because they structure the text and do not emphasize it.
- Headings: lead with keywords, keep them under about 65 characters, and make each one unique. Do not end a heading with punctuation.
- Bulleted lists:
    - Start with an intro sentence that ends in a colon.
    - Keep one idea in each item.
    - Start a fragment with a lowercase letter and leave off the period.
    - Start a full sentence with a capital letter and end it with a period.
    - Do not mix fragments and full sentences in one list.
    - Do not add "and" or "or" after an item.
- Numbered steps: use them only when the order matters. Make each step a full sentence that starts with a verb.
- Links: write link text that says where the link goes, with keywords first. Never write "click here" or "read more".
- Write "for example", "that is", and "and so on", not "e.g.", "i.e.", and "etc."
- Write "and", not "&", except in an official brand name.
- Expand an acronym on first use unless the whole audience knows it. Avoid slashes such as "and/or" and "he/she".
- Do not give an instruction by color, position, or shape alone ("the green button on the right"). Name the element.
